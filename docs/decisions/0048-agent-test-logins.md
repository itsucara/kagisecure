## Context

The owner wants Claude Code, working on the Mac, to create test users for the apps it is testing,
to have **kagisecure generate and keep the password**, and to reuse those test users in later test
runs — with no tool ever returning the password to the agent. The agent knows the app, the purpose
and the username it wants; it should not choose, see or hold the password.

[ADR-0046](0046-agents-propose-item-drafts.md) as written cannot serve this. It lets an agent
propose an item, but the secret is typed or generated by the person on an editor sheet, and every
draft pays a Touch ID with no grace window. It lists "the agent generates the password and passes
it in" as out of scope. A test loop that creates a user per app and signs in dozens of times a day
would be a sheet per user and a fingerprint per draft — the approval fatigue ADR-0036 §9 counts as a
cost, not a safety margin. Separately, `request_fill` refuses registration forms by design
(the extension's `new-password` disqualifier), and `describe_item` never returns a username.

ADR-0046's caution is built around one threat: an agent-supplied URL becomes the autofill match
target for a **real** password — one the person later types for the real site, or reuses — and a
look-alike domain then collects it. That threat does not exist for a value kagisecure generated
itself, inside the vault, that has never protected anything else, and that is never offered to the
person. What replaces it is narrower and different: a planted item offered to the person anyway; a
person later putting a real password into a test item; "test" logins created on real services; an
agent rigging the generator or flooding the vault; and the honest fact that an agent driving the
page or the command can read what kagisecure types there. This ADR contains each of those
mechanically, so that the remaining test loop can run without sheets.

## Decision

### 1. A Settings switch, off by default

"Agent test logins" is a switch in Settings, **off by default**. Turning it on asks for one
presence proof (the precedent is `PresenceOwner.featureSwitch`, which the unattended switch uses).
Turning it on creates the vault of §2 if it does not exist. The policy — the switch and the allowed
domains of §3 — lives inside the encrypted vault, in that vault's `VaultMeta.purpose`, not in app
defaults, and every change to it is a transactional, audited write.

With the switch off, the tools of §6 that create, list or trash answer `TEST_LOGINS_OFF` before
anything is looked up, and no fill or run takes the paths of §7 or §9. Items already created stay.

### 2. One dedicated personal vault: "Agent test logins"

Test logins live in one personal vault, created by the switch and recognised by
`VaultMeta.purpose = AgentTestLogins` — never by its name, which the person may rename. It is
agent-visible and shows new items to agents. The tools of §6 take **no vault argument**: an agent
cannot direct a test login into the person's own vault, and nothing here writes to a shared vault
(ADR-0035 §14 stands; a shared vault is refused wherever one could be named). Environments for test
apps (§9) are created in this vault too, so bindings to test logins never cross vaults.

### 3. Allowed origins: where no sheet is needed

The no-sheet paths of §6, §7 and §12's cleanup apply only when **every** website involved is one of:

- a loopback origin (`127.0.0.0/8`, `[::1]`) or `localhost`;
- `*.localhost` or `*.test` (names that cannot resolve to someone else's service);
- a registrable domain (eTLD+1 by [ADR-0022](0022-public-suffix-list.md)'s public suffix list) that
  the person has added to the allowed list in Settings; adding one asks for presence.

Private LAN ranges and single-label hosts other than `localhost` are not on the list. Any other
origin gets an
ADR-0046-style sheet for the create: the agent's identity, the registrable domain **large** above
the full URL, ADR-0046 §5's near-host and non-`https` flags, and Touch ID every time. Real services
and employees' SaaS accounts are therefore never on the fast path; a person who allows a create
there is making the decision ADR-0046 asks of them.

### 4. Generation: a fixed menu, inside the vault transaction

The agent may choose a length from a fixed menu — **20, 24, 32, 48 or 64** — and whether to include
symbols and avoid ambiguous characters, so it can match an app's password rules. The default is
32 characters with symbols. Lowercase, uppercase and digits are always on. Every menu choice clears
an entropy floor of **at least 100 bits**, checked with the generator's own `entropy_bits()`. There
is no custom alphabet, no seed, no "words" recipe and no argument that could carry a value. The
password is generated by the existing `kagisecure_core::generator` inside the vault transaction
that writes the item, and goes straight into the concealed field; it never crosses FFI, IPC or MCP.

### 5. The seal

At creation kagisecure seals the item: HMAC-SHA256 under a key derived from the vault key with a
fixed info string (`crypto::derive_subkey`, as the body key is derived), over the item id ‖ the
primary-secret field id ‖ the password bytes. The seal is stored with the item's provenance in
`Item.extra["agent_test_login"]`: `{v, seal, created_by, created_at, app, purpose}`, where
`created_by` is the agent's identity (§10). The precedent for provenance in `extra` is the
`copied_from` marker that ADR-0042's machine-vault logins carry.

The seal is checked, in constant time, at every fill and every binding release that relies on it.
A **sealed** item is one whose seal verifies. An item whose password was edited, replaced or moved
no longer verifies, and from then on it is an ordinary item: the rules of ADR-0036 and ADR-0047
apply to it exactly as to any other login.

### 6. The tool contract

- **`create_test_login`** `{ app, purpose, username, websites[1..5], generator?: { length:
  20|24|32|48|64, symbols?, avoid_ambiguous? }, tags?, reason? }` →
  `{ status: "created" | "exists", item_id, username, websites, title }`.
  kagisecure composes the title, `test: <app> / <purpose> #<n>`, and the tags `agent-test`,
  `app:<app>` and `purpose:<purpose>`; the agent's own `tags` are added beside them. `purpose` is
  stored as a **public**, length-capped field checked with `display_text_ok` — not in notes, which
  are secret and unsearchable, so the agent could never find the item by it again; notes stay free
  for the person. If a sealed item with the same username already covers the website, the result is
  `status: "exists"` with that item, and nothing is written: this is how a test user is reused per
  app. The argument is named `generator`; no argument name offers a value.
- **`list_test_logins`** `{ website?, tag?, query?, limit?, cursor? }` → sealed items in the test
  vault only, each with `item_id, title, username, websites, tags, purpose, created_at`.
- **`request_fill`** gains `fields: ["username", "new_password"]` or `["new_password"]` for sign-up
  forms (§7). The existing `["username", "password"]` serves login. `new_password` is never combined
  with `password` or `one_time_code`, and there is no `mode` argument.
- **`trash_test_logins`** `{ website?, tag?, reason }` → `{ trashed, item_ids }`; sealed test-vault
  items only, in one transaction (§12).

The username comes back from `create_test_login` and `list_test_logins` because the agent chose it
and needs it to drive the page; these are separately named tools, so `describe_item` is **not**
widened and keeps returning metadata only (ADR-0002). No tool returns the password, in any
encoding, under any argument. Non-browser tests use the existing tools: `create_environment` (in the
test vault), `add_variables` with `bind_to { item_id, field_id }`, then `run_with_env` (§9).

The test user must exist in kagisecure **first** and in the app second — by a sign-up fill or by
seeding through `run_with_env`. An agent that created the user in the app first would have chosen
the password itself, which is exactly what this design avoids.

### 7. Fills of a sealed item at an allowed origin

A login fill or a sign-up fill of a sealed item, at an origin that passes §3, needs **no sheet and
no presence proof**. Every other gate of ADR-0036 runs as before — the agent-fill switch, the item,
the fields, the connected browser, the tab (top frame, origin byte-equal to the claim, a saved
website covering it), ADR-0040's audit pre-flight and the delivery re-checks. Only gate 8 differs:
instead of asking the queue, the broker spends a pass issued for this item and origin, and releases
through a new constructor, `Approved::from_test_login` — the shape of ADR-0042 §12.6's
`Approved::from_standing`, a second, structurally separate way to an `Approved` that no other item
can reach. It never fakes a person's Grant, and `Approved::from_grant` is unchanged. Such a fill
raises no sheet. A fill of a sealed item at an origin outside §3 goes through ADR-0036's ordinary
path, as amended.

- **Sign-up mode** writes the same generated value into every new-password box of a recognised
  sign-up form — one `autocomplete="new-password"` field, or exactly two password fields. It is
  served only for sealed items; an unsealed item answers `NOTHING_TO_FILL`. It is refused when the
  form has a `current-password` field, three or more password fields, or anything the login
  detector also accepts. The ten-second tripwire of ADR-0036 §8.3 watches every box written.
- **Login fills** keep the rule their tests pin: a login fill never lands in a new-password box.
- ADR-0036 §8.3 is unchanged: kagisecure types and stops; the agent presses the button.
- `NO_MATCHING_TAB` stays one code with one message, whatever the reason the form did not qualify.

### 8. Hidden from the person's autofill

Items in the test vault are **never offered to the person**. They are excluded from the extension's
human match path (`matches()` and `is_servable` refuse them) and from the system AutoFill identity
store (the macOS credential provider returns nothing for them). The iOS provider on
`feat/ios-autofill` must adopt the same exclusion before it merges. The person still sees the items
in the app, with their provenance, and can reveal and type one by hand. An older client that
predates this rule may still offer them; that is accepted, since the value is random and never
anyone's real password.

### 9. Non-browser tests

Binding a test login to an environment variable with `add_variables` keeps its sheet, once per
environment: a binding is a standing route to the value and the person sees it made. A
`run_with_env` or `write_env_file` request whose **every** selected variable is bound to a sealed
test login — environment or stdin delivery — rides ADR-0037's app-wide grace window the way agent
fills do: inside the window it raises no sheet and asks for no Touch ID; outside it, the sheet and
Touch ID as today. It never becomes a standing permission, because the command is the agent's:
every run outside the window is approved on its own, ADR-0047 §4's single use for stdin stands, and
the audit entry records the command either way. A request that selects any other variable is
unchanged.

### 10. Audit and notice

Every create, fill and trash of a test login carries the agent's full identity — the `actor_for`
form agent fills already use (`mcp` followed by the peer's self-reported name and kernel facts),
not the bare `mcp` and pid of ordinary tools — and is committed before the write or release it
records (ADR-0040; a failed audit fails closed). Details are fixed tokens:
`TEST_LOGIN_CREATED (automatic)` or `(approved)`, `TEST_LOGIN_FILL (automatic)` and
`(automatic, sign-up)`, `TEST_LOGINS_TRASHED matched=n`. Switch and allowed-domain changes are
audited too. Creates raise a passive notice — a system notification and a menu-bar entry
("N test logins created by agents") — that asks nothing of the person.

### 11. Caps

Creates are rate-limited per agent — **10 in any 10 minutes** — keyed on the sidecar's kernel
identity rather than the per-call IPC connection, so reconnecting does not reset the count. The
test vault holds at most **200 live items** (trashed items do not count). Both answer
`RATE_LIMITED` with their own fixed message.

### 12. Personal and interactive only

Nothing here exists on the unattended socket: `create_test_login` and `trash_test_logins` answer
`NO_GRANT`, `list_test_logins` returns nothing, and the debug-only `--auto-approve` refuses the
create kind as it refuses `AgentFill`. There is no tool that updates, merges or deduplicates a test
login beyond §6's `exists`. Cleanup, when an environment is rebuilt, is `trash_test_logins`: a
**soft trash**, automatic only when every matched item's websites pass §3 and otherwise refused.
Not archive — archived items refuse fills, so an archived test login would be dead weight — and
not deletion: emptying the trash stays the person's act.

## What the person sees

1. In Settings, the person turns on **Agent test logins** — Touch ID once. The vault "Agent test
   logins" appears.
2. Testing a local shop app, Claude calls `create_test_login` (`app: "shop"`, `purpose: "buyer"`,
   `username: "buyer1@example.test"`, `websites: ["http://localhost:47800"]`).
3. A notification reads "“Claude Code” created test login “test: shop / buyer #1” for
   localhost:47800". No sheet.
4. Claude navigates to the app's sign-up page and calls `request_fill` with
   `["username", "new_password"]`. kagisecure fills the email box and both password boxes; Claude
   presses **Create account**.
5. In a later session Claude calls `list_test_logins` (`tag: "app:shop"`), finds the buyer, opens
   the login page and calls `request_fill` with `["username", "password"]`. It signs in.
6. Throughout: zero sheets, zero prompts after the first Touch ID.

The contrast: Claude calls `create_test_login` for `https://staging.example-partner.com`, a domain
not on the allowed list. A sheet opens with the agent's identity and **example-partner.com** in
large type above the full URL; creating it needs Touch ID, and so does every later create there.

## Threats

- **A planted look-alike item offered to the person.** Mitigated by §8: test-vault items are never
  matched for the person's own fills, so an agent-chosen URL is not an autofill target for them.
- **The person later types a real password into a test item.** The seal (§5) stops verifying and
  every exemption drops; the item is ordinary from then on. The app offers only **Regenerate** for
  the sealed password field, and items cannot be imported or moved into the test vault.
- **Same-title confusion.** Titles are composed by kagisecure (`test: <app> / <purpose> #<n>`), live
  in their own vault, and carry provenance in the app; an agent cannot title one "GitHub".
- **The agent reads the value from the page, its own command, or the app's database or logs.**
  ACCEPTED. kagisecure never returns the password through any tool, so a well-behaved agent keeps it
  out of its transcript and the provider's logs. It types the value into a page the agent drives, or
  pipes it to a command the agent chose, and the app under test receives it. An agent that runs
  script in that page, chooses that command, or controls that app can read it. Agent test logins
  accept this: the value is random, protects only a test account on a site you allowed, and is never
  anyone's real password.
- **A "test user" on a real service.** Excluded from the fast path by §3; a create there is an
  ADR-0046-style sheet with the registrable domain shown large and Touch ID.
- **Rigged generator settings.** §4's fixed menu and the 100-bit floor; no alphabet, no seed.
- **Flooding the vault or the notices.** §11's per-agent rate limit and live-item cap.
- **Shared vaults.** §2: no vault argument; shared vaults are never written.
- **Purpose text as persistent prompt injection.** `purpose` is a public, capped,
  `display_text_ok` field, presented in tool results and the app as agent-written data, never as
  instructions.
- **An audit gap for ordinary tools** (which record only `mcp` and a pid). §10 closes it for these
  tools; the wider gap is recorded elsewhere.
- **A new-password fill into a change-password form of a real account.** Refused by the
  `current-password` rule (§7), and it would add no capability: only sealed values are ever filled
  in sign-up mode, and an agent already controls the page.
- **Shared localhost ports** (another local process listening on the saved port). Accepted for
  random test values; private LAN ranges are excluded from §3.

## Out of scope

- Real-service accounts and employees' SaaS accounts: the ADR-0046 path.
- Shared vaults and the machine vault.
- Unattended use and headless hosts ([ADR-0043](0043-unattended-access-on-headless-hosts.md)).
- Native-app fill through the credential provider: ADR-0045 is not enabled on a real Mac and has no
  new-password flow. Today, XCUITest or API tests with credentials delivered to the test process
  through `run_with_env` are the way.
- Passkeys.
- Agent edits of existing items.
- Permanent deletion.
- The itsustar AI room.
- Per-client policy: the switch is global to MCP clients today; a per-client switch can be added
  later without changing this design.

## Consequences

### Positive

- Test loops run with zero sheets: one Touch ID turns the switch on, and creates, sign-ups and
  logins at local and allowed origins need nothing more.
- No secret crosses MCP; ADR-0002's canary tests apply unchanged.
- Every agent-created test login is attributable, in the audit log and on the item.

### Negative — accepted

- A second vault with special rules, and a second release path (`Approved::from_test_login`).
- `PROTOCOL_VERSION` goes to 4, so the sidecar, the app, the extension and the native-messaging
  host ship together.
- The sign-up detector is strict: single-page-app forms without `autocomplete` hints or a `<form>`
  fail safe as `NO_MATCHING_TAB`, and the agent falls back to seeding through `run_with_env`.
- A new vault-level invariant (§8) that older clients do not know.

### Risks the implementer should expect

- The 60-second approval timeout on the sheet path; there are no pending drafts, so the agent
  retries.
- Protocol 4: a stale sidecar is refused at `Hello`, so the sidecar, app, extension and
  native-messaging host ship together.
- The four existing agent-fill e2e scenarios are written but have never run in a real browser;
  the harness will need work before the new scenarios run.
- The three Swift files touched by ADR-0047 (`ApprovalSheet.swift`, `AgentService.swift`,
  `CHANGELOG.md`) are on `main` as of `4148b3e`; edit on top of that.
