# Security policy

## Status

kagisecure 0.1.0 is the first release. It is early software: the vault format is not yet frozen,
and [docs/threat-model.md](docs/threat-model.md) records what the design does and does not defend
against. Reports about the design are as welcome as reports about the code.

## Reporting a vulnerability

**Do not open a public issue for a security problem.** Report it privately, by either of:

- **GitHub private vulnerability reporting** — the "Report a vulnerability" button on this
  repository's Security tab.
- **Email** — [security@kagisecure.com](mailto:security@kagisecure.com).

Please include:

- A description of the issue and why it is a security problem.
- The affected component and version, or the document and section for a design flaw.
- Reproduction steps or a proof of concept, if there is code.
- Your assessment of impact, and any suggested fix.

## What we consider in scope

Everything in the threat model's adversary list: a malicious or compromised agent, prompt
injection via tool results, local malware running as the user without root, another local user,
a lost device, and a malicious MCP client. In particular:

- Any way to obtain a secret value through the MCP surface.
- Any way to cause an injection without a valid approval or lease.
- Any weakness in the vault format, key hierarchy, or KDF parameters.
- Secrets appearing in logs, error messages, crash output, or the audit log.
- Privilege issues in the IPC channel, or a way to impersonate an approved client.
- Anything that makes the approval prompt misleading about what is being approved.

## What is out of scope

These are stated as explicit non-goals in [docs/threat-model.md](docs/threat-model.md) §4 and are
not accepted as vulnerabilities:

- Root / Administrator / kernel compromise.
- A debugger attached to the running app, or a machine with SIP / Secure Boot disabled.
- Hardware attacks: cold boot, DMA, Secure Enclave or TPM breaks.
- The contents of a `.env` file after kagisecure has written it, or the environment of a process
  after kagisecure has spawned it.
- Item and field *names* being visible to agents — this is disclosed by design.
- The user choosing to paste a secret into a chat themselves.
- Reports generated by automated scanners with no demonstrated impact.

## Disclosure

We aim for coordinated disclosure:

| Step | Target |
| --- | --- |
| Acknowledge the report | 3 business days |
| Initial assessment | 10 business days |
| Fix and release for a confirmed critical issue | 90 days, sooner where practical |
| Public advisory + credit | On release of the fix |

We will credit reporters who want credit. There is no bug bounty — this is an unfunded open-source
project, and we would rather say so than imply one exists.

## Supported versions

Only the latest release receives security fixes. While kagisecure is below 1.0.0, a fix ships as
a new release rather than as a patch to an older one.
